# Code audit — 2026-08-19

Four parallel audits (C# manager, C# packet decoder, C# host+UI, Lua driver) against this
project's own hard rules. Findings are recorded here so none are lost; fixed ones are struck
through with the commit.

Rules used as the criteria (from CLAUDE.md):
1. NO HARDCODED game facts (npc/mob/item/skill ids, maps, coords, prices)
2. ZERO IS A VALID VALUE — never a sentinel
3. Wiring an action means wiring its RESULT packet
4. A `-1`/"unknown" fallback is a DECODE GAP, not an acceptable state

Bug shapes searched for, all proven real in this codebase today:
A comment/log contradicts the code · B stale state read as an answer · C guard cleared by the
action it gates · D lifetime (work outliving its session) · E event emitted before the state it
describes · F decision treated as an outcome

## POSTSCRIPT 2026-08-20 — what the audit got right, and what it missed

The morning after this audit the live bot was found **hard-wedged for 9.4 hours**: frozen at
`(5899,6530)` in RouN, `sell:travel-to-town` 97% of 34,475s, +0 exp, 0 deaths, 45 CRITICAL lines,
and `MAP-CHANGE LOOP: Eld -> RouN (5x in 60s)` repeating for the whole window.

**The audit predicted a wedge of exactly this shape** (HIGH #1: hardcoded `SELL_NPC = 29` used raw,
so a bag-full trip cross-maps to npc29’s town and, if selling never succeeds, the bag stays full and
per `fiesta-bagfull-blocks-everything` the whole quest loop halts). That prediction was close enough
to be dangerous: **it was not the cause.** Reaching for it would have shipped a real improvement and
left the bot wedged.

The wire said something else. Two lines from the same instant:

```
07:25:14.678 CRUTCH[CRIT] HARD-WEDGE: pos @(5899,6530) ... phase=sell:travel-to-town map=Eld
07:25:08.102 ⛔ WATCHDOG: MOTIONLESS for 45s at (5899,6530) on RouN
```

The Lua thought it was on Eld; the host knew it was on RouN. `mapOf()` preferred `pulse.map`, and
`pulse` is refreshed only by `questSnapshot()`, called from the quest-scoring loop **late** in
`tick()`. The sell branch returns before that loop — so the bag filled on Eld, the snapshot froze
with `map = "Eld"`, `sellLoot()` read the frozen value while standing in RouN, travelled to RouN,
returned early again, and the only code that could have corrected the stale map sat behind the branch
the stale map kept taking.

That is bug shape **C** from the list above (a guard cleared only by the action it gates), and it is
the same shape as `fiesta-gate-depends-on-what-it-gates`. The audit hunted shape C in the C# and
found it in `ObserveGates`; it did not look for it across the Lua caching layer, which is where the
expensive instance was. **Caches are guards**: "is this value fresh" is gated by the code path that
refreshes it.

Fixed in the lua repo (`freshPulse()` — a cached answer is only an answer for the tick it was taken
on) and in `ConfirmHopArrival` on the C# side. Verified live: position moved within one minute of
applying, exp 173,900 -> 174,038.

Two process notes worth keeping:
- **An audit finding that matches the symptom is not a diagnosis.** HIGH #1 described this exact
  failure mode in advance and was still the wrong answer; only the interleaved log settled it.
- The `HARD-WEDGE` line blames "client<->server position DESYNC". That is the detector’s **guess**,
  printed as though it were a reading. It sent the first pass of this investigation the wrong way.
  A diagnostic should report what it measured (position and exp frozen) and not name a cause it has
  not established.

## HIGH

**1. L388 — `local SELL_NPC = 29` (Rule 1, hardcoded NPC id).**
`local SELL_NPC = 29  -- soul-stone Healer Julia (RouN)`
This is the *same bug as `HEALER = 29`, but unmitigated*: `HEALER` is at least demoted to a fallback seed behind `nearestServiceNpc("soulstone", HEALER)` (L5014), whereas `SELL_NPC` is used raw as the sell target — `serviceMap(SELL_NPC)` (L4283), `bot.npcLocation(SELL_NPC)` (L4291), `bot.npcByMob(SELL_NPC)` (L4299), and it is even seeded into the town set at L2236. Every bag-full sell trip therefore cross-maps back to npc 29's town from wherever the bot is, and on any map/server where npc 29 doesn't exist selling never happens at all (`sellLoot` returns false at L4289 forever → bag stays full → per `fiesta-bagfull-blocks-everything`, the whole quest loop halts). `knownShopsOfKind("item"/"weapon")` already answers this by role.

**2. L337, L339 — `XPFIELD = "RouCos02"`, `AVOID_MAP = { EchoCave = true }` (Rule 1, hardcoded map names).**
`xpGrind()` (L3999-4003) travels to `XPFIELD` whenever nothing is huntable — at *any* level, from any map, ignoring mob levels. This is the level→zone band the rule explicitly bans; the data to pick a field (mob levels + `spawnMaps` from `questStatics`, plus `mapCaps.enemyMobs` which the script already learns at L3962) is in hand.

**3. L3039-3044 — the "DEMOTED on OBSERVED lethality" log is a lie (Shape C).**
```lua

...
local risky = deprioritized or swarmRisk      -- lethalMob is NOT in here
```
`lethalMob` is computed (L3029), logged as a demotion, counted in `riskCensus.lethal` — and never affects `band` (L3051). The quest keeps full priority. L3043's own comment says the disqualifier was "reverted"; the log line wasn't. Any future investigation reading the tail will believe lethal quests are being demoted when nothing happens.

**4. L1944 — RETALIATE log claims "WITHOUT walking (route/kite preserved)" (Shape C).**
```lua
crutch("OK", "RETALIATE in place: ... auto-attack + skills WITHOUT walking (route/kite preserved)")
```

The function's *own* header at L1889-1891 states the opposite and explains why it killed the bot: "This function claims it attacks 'WITHOUT walking' and that is not true: bot.autoAttack -&gt; FaceAndStopAsync sends a 16u face-step and then an ActStop." **5. L314 + L2506-2527 — `fleeing` is never set to `true`; the whole FULL-FLEE state machine is dead (Shape G + C).**
`local fleeing = false` is only ever assigned `false` again (L2508, L2515). ~22 lines of flee/recover logic (`bot.flee(FLEE_DIST)`, the aggressor-clear resume, `FLEE_DIST`, `FLEE_SAFE_PCT`) can never execute, and the comment "true during a FULL retreat from being overwhelmed" describes behaviour that does not exist. `shedStep()` replaced it but the corpse still gates L2529 (`if not fleeing and ...`).

**6. L3782-3799 — a measured "we die in &lt;15s" verdict is discarded by a mob COUNT, silently (Shape D + Rule 4).**

`shedStep()` bails at `if n &lt; SHED_MIN_PACK then return false end` (L1997, n&lt;3). The arithmetic the whole section was built around is overridden by a count, in exactly the direction that kills the bot, with no trace.

**7. L1369 — `engagedAt or bot.now()` never falls back, because 0 is truthy (Rule 2).**

## MEDIUM

**14. L5401 — the accept-walk progress epsilon is larger than the distance that remains (Shape G).**
```lua
if not pr or dnow &lt; pr.d - NPC_RNG then   -- NPC_RNG = 200
```
The walk loop only runs while `dist &gt; NPC_RNG (200)`, so inside ~400u of the giver no closing step can ever satisfy `dnow &lt; pr.d - 200`; after `ACCEPT_NAVSTUCK_MS` (20s) the quest is shelved for 3 minutes as "NAV-STUCK" *while the bot is visibly walking toward the giver*. This is the identical bug the probe path already diagnosed and fixed at L4409-4417 ("the stall guard needed 30u of closing while only ~19u remained — a threshold bigger than the distance it measures"); the fix (`need = max(4, min(30, (d0-range)*0.4))`) was never applied here.

**15. L1063 — `if useClass == 0 then return true end` (Rule 1, a hardcoded game fact that contradicts client data).**
`usableByUs` short-circuits UseClass 0 as "usable by every class" *before* asking `bot.canUseClass`, which reads the client's own `UseClassTypeInfo` matrix. Per that matrix, **1** is the all-class value and **0** allows nobody (`UseClassAllows` returns the flag column verbatim; `ClientData.cs:757` even uses `useClass == 1` as the all-class fallback). If that reading is right, this line makes the bot buy/equip/keep items no class can use. Worth confirming against `UseClassTypeInfo.shn` row 0 before changing — but it should be a `canUseClass` call either way, not a baked branch.

**16. L1400, L1498, L1733 — `(si.useClass or 0) &gt;= 2` drops all-class skills.**
`damageSkillCount`, `castRotation`'s admit gate and `rangedPuller` all require `useClass &gt;= 2`. A skill with UseClass **1** (usable by everyone) is silently excluded from the rotation, from the damage-skill count that drives `MAGE_NO_AA_SKILLS`, and from pull selection. Same root as #15: a hand-rolled band instead of the matrix.

**17. L1609 — the cast is confirmed in the same tick it is sent (Shape E).**
```lua
bot.attack(id, castTarget)
if not bot.castConfirmed or bot.castConfirmed() then castAt[id] = bot.now(); castTry[id] = nil end
```
`castConfirmed()` reads `View.CastServerConfirmed` — state from a *previous* cast; the server's answer to the send that happened microseconds earlier cannot have arrived. So the spam window is ended on a stale confirmation, and the cooldown is banked for a cast that may have been rejected.

**18. L1448-1455 — `buffWorthCasting()` stamps the backoff on the decision, not the cast (Shape E).**
`buffCastAt[id] = bot.now()` is written inside the *predicate*. The caller (L1497) may still drop the skill on `sp &gt;= si.sp`, cooldown, `usableDegree`, `damageOnly`, or by losing the `ranked` sort — and the 120s "cast it but couldn't verify" backoff starts anyway, along with the WARN claiming "cast it, but its abstate never appears".

**19. L2621 vs L1896/L3791 — `survivalShedAt` is stamped in only one of the two shed call sites (Shape C).**
L1896 says "grindStep stamps it after shedStep returns true" — grindStep does not; `clearTail` does (L3783-3791), and `tick()`'s own `elseif shedStep() then return end` (L2621) stamps nothing. So retaliation stands down for some sheds and not others, and the comment points at the wrong function.

**20. L601/L683 + L705/L721-727 — duplicate declaration makes the KQ-phantom crutch unreachable (Shape G).**
`local unsolvableLogged = {}` is declared twice (L601 is then dead). Inside `noteUnsolvable`, L705 sets `unsolvableLogged[id] = true` unconditionally, then L723 tests `if not unsolvableLogged[id] then` before the phantom message — always false. The `"UNSOLVABLE (KQ/phantom kill mob...) — SKIPPING this quest ... (logged once per session)"` line can never print; only the `else` branch (L729) ever logs.

**21. L154-156 + L3000 — the documented deprioritization expiry does not exist (Shape C + G).**

The comment explains the chicken-and-egg it exists to break ("the C# store only clears on LEVEL-UP, which chicken-eggs the bot into a last-resort grind"). **23. L4180 — `bot.hasSkill(sk)` omits the passive flag.**

## Findings

### HIGH

**1. `BotManager.cs:453, 469, 480, 748, 1570, 1583, 2199` — shape A + rule 3: `ActionResult.Sent` returned when nothing was sent**

Seven call sites return the enum member literally named `Sent` on the *refusal* path (cooldown, out of range, bash-windup defer, full HP/SP, cast-bar walk suppression). `Scripting/BotApi.cs:595` is `Ok(r) =&gt; r == ActionResult.Sent`, and `bot.cast/autoAttack/soulstoneHp` all go through it — so the Lua rotation is told "yes, it cast" for a cast that never hit the wire. **2. `BotHandle.cs:135-148` — phase-time accounting double-counts quadratically, then silently stops**
```csharp

if (d &gt; 0 &amp;&amp; d &lt; 3600) _phaseSeconds.AddOrUpdate(prev, d, (_, v) =&gt; v + d);
```

`_phaseSinceUtc` is only reset when the phase **changes**, but `NotePhase` is called every tick with the same phase (line 139's own comment says so).
